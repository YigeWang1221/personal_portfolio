## 系统概览 {#overview}

应用本身是一个 REST API，管理用户、商品、商品图片和邮箱验证。真正值得看的是它周围的一切：

- **计算。** Spring Boot 运行在 Packer 构建的机器镜像上，部署在私有子网中、跨 {{fact:azs}} 个可用区的 Auto Scaling 组里（三到五台实例），前面是 HTTPS 应用负载均衡器和 Route 53 别名记录。
- **数据。** RDS MySQL 存储业务记录，用 Flyway 管理迁移，Hibernate 只做结构校验；S3 存放商品图片，三十天后转入 Standard-IA 存储层。
- **密钥与机密。** {{fact:kms_keys}} 把客户托管的 KMS 密钥；数据库密码由 Terraform 生成并存入 Secrets Manager。
- **邮件。** 用户注册时发布事件到 SNS，由 Lambda 函数通过 Mailgun 发送验证邮件。
- **两个 AWS 账号。** 镜像在 dev 账号构建，再晋升到 demo 账号。

除了 SNS 主题和 TLS 证书是手动创建的，其余全部由 Terraform 定义。

## 交付过程 {#planning}

这门课由九次作业组成，我把每一次都当作一个里程碑，用各自的 PR 交付。提交历史读起来就像一份路线图：先是带测试的 API，然后是 CI，接着是镜像与基础设施即代码（IaC），再到数据层、可观测性、负载均衡，最后是事件、密钥和无服务器邮件。每一步都通过 PR 合入。

## 关键决策 {#decisions}

| 决策 | 选择 | 取舍 |
|---|---|---|
| 发布方式 | 不可变 AMI + 实例刷新滚动上线 | 比原地更新服务器慢；每次发布都可复现，回滚容易 |
| 环境划分 | dev 与 demo 两个独立 AWS 账号，共享 AMI | IAM 配置更多；dev 里的失误影响不到 demo |
| 可用性与成本 | 应用层跨三个可用区；RDS 单可用区；只用一个 NAT 网关 | NAT 网关或数据库所在可用区故障会导致服务中断；固定成本低得多 |
| 机密管理 | Secrets Manager + KMS，数据库密码在启动时获取 | 启动依赖 AWS API；镜像里不包含数据库密码 |
| 邮件发送 | SNS → Lambda → Mailgun，而不是在请求中直接发送 | 多了一个第三方依赖；注册接口的延迟不受邮件投递影响 |

## 我负责的部分 {#ownership}

全部。这是个人课程作业：API、Terraform、Packer 模板、工作流和 Lambda 函数都由我编写，三个仓库里的每一次提交和每一个 PR 都出自我手。课程期间这些仓库的 CI 共运行了{{fact:ci_runs}} 次。

## 跨账号的不可变发布 {#pipeline}

- **每个 PR** 触发两个工作流：一个在 JDK 21 和 MySQL 服务容器上运行测试，另一个用 `fmt`、`init`、`validate` 检查 Packer 模板。
- **合并之后**，流水线构建 jar，在 dev 账号用 Packer 构建 AMI，再共享给 demo 账号。Packer manifest 把新的 AMI ID 传给下一个任务。
- **在 demo 账号中**，流水线创建新的启动模板版本并设为默认，发起实例刷新（替换过程中保持足够的健康容量），然后等待刷新完成。

一次成功部署的中位耗时为{{fact:deploy_median}}。因为没有"之前"的测量，我直接给出耗时本身，而不是百分比提升。

有一个细节需要说明：测试在 PR 阶段运行，合并后的构建为了节省时间会跳过测试，PR 检查才是真正的关卡。

## 安全设计 {#security}

- **每个服务一把 KMS 密钥**：S3、实例磁盘、RDS 和 Secrets Manager 各用一把，并自动轮换。
- **镜像里没有密码。** 数据库密码由 Terraform 生成并存入 Secrets Manager；实例启动时，user data 把它取到本地权限受限的环境文件里。
- **用引用划定网络边界。** 安全组之间互相引用，而不是写 CIDR 网段：负载均衡器面向公网，实例只接受来自负载均衡器、发往应用端口的流量，数据库只接受来自实例和 Lambda 的连接。
- **按组件划分的角色权限。** 实例角色只能访问自己的存储桶、密钥、一个机密和一个 SNS 主题。日志和指标权限仍使用通配符，密钥策略也比实际需要的宽，详见最后一节。
- **不开放 SSH。** 实例没有公网 IP；SSH 规则和明文 HTTP 监听器在开发过程中都已移除。

## 可观测性 {#observability}

两个基于 AOP 的拦截器分别测量每次控制器调用（按状态码计数并计时）和每次仓储层调用（成功数、错误数和耗时）。Micrometer 通过 StatsD 把指标发给 CloudWatch agent，应用输出结构化 JSON 日志，由 agent 发送到 CloudWatch Logs。CPU 告警驱动逐台扩容和缩容的伸缩策略。系统没有做监控看板：指标可以画图，但我没有搭建看板。

## 异步邮件验证 {#email}

用户注册时，API 向 SNS 发布一个事件后立即返回。VPC 内的 Lambda 函数（Python）接收事件，通过 Mailgun 发送验证链接；链接中带有一次性、很快过期的令牌。这个函数有自己的 CI 工作流，先把新版本发布到 dev 账号，再发布到 demo 账号。

## 取舍、不足与下一步 {#limits}

- **有意保留的单点故障。** 单个 NAT 网关和单可用区数据库让课程作业的月度成本保持在低位；生产版本应当把两者都分布到多个可用区。
- **平铺的 Terraform。** 配置是一个根模块，状态保存在本地。下一步：拆分成可复用的模块，并使用带锁的远程状态。
- **长期有效的 CI 密钥。** 工作流使用存为 secret 的访问密钥。我会改用 GitHub OIDC 联合身份，后来在 KK Knock 的流水线中我就是这样做的。
- **测试偏少。** 三个 REST Assured 测试类覆盖正向流程、反向流程和边界情况（包括一次并发请求突发），没有单元测试，也没有覆盖率报告。
- **IAM 权限偏宽。** 日志和指标权限使用通配符，KMS 密钥策略给了实例角色超出需要的权限，两者都应收紧。
- **先测量，再下结论。** 部署耗时和成本从未与基线对比过，所以本页只报告提交历史能证明的内容。
