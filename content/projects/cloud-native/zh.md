## 服务与核心问题 {#overview}

应用本身是一个 REST API，管理用户、商品、商品图片和邮箱验证。真正值得看的是它周围的一切：一次改动如何从 PR 走到正在运行的机器上，以及每个运行中的组件被允许访问什么。

- **计算。** Spring Boot 运行在 Packer 构建的机器镜像上，部署在私有子网中、跨 {{fact:azs}} 个可用区的 Auto Scaling 组里（三到五台实例），前面是 HTTPS 应用负载均衡器和 Route 53 别名记录。
- **数据。** RDS MySQL，用 Flyway 管理迁移，Hibernate 只做结构校验；S3 存放商品图片。
- **邮件。** 用户注册时发布事件到 SNS，由 Lambda 函数发送验证邮件。
- **两个 AWS 账号。** 镜像在 dev 账号构建，再晋升到 demo 账号。

除了 SNS 主题和 TLS 证书是手动创建的，其余全部由 Terraform 定义。

## 课程规定了什么，我做了什么 {#ownership}

这是由九次作业组成的个人课程作业。里程碑和很多需要构建的内容由作业规定，所以我不把工作顺序说成自己制定的产品路线图。在这个范围内，所有实现都由我完成：API、Terraform、Packer 模板、工作流和 Lambda 函数。三个仓库里的每一次提交和每一个 PR 都出自我手；课程期间这些仓库的 CI 共运行了{{fact:ci_runs}} 次。

本页说"选择"时，描述的是代码实际怎么做以及代价是什么，并不是说课程对每个方案都没有要求。

## 从合并的 PR 到运行中的实例 {#delivery}

发布时没有人需要登录服务器。一次发布就是一个新的机器镜像，由 Auto Scaling 组用它替换现有实例。

1. **每个 PR** 触发两个工作流：一个在 JDK 21 和 MySQL 服务容器上运行测试，另一个用 `fmt`、`init`、`validate` 检查 Packer 模板。这些检查就是关卡：合并后的构建不会再跑一遍测试。
2. **合并后，在 dev 账号中**，工作流构建 jar，Packer 把 jar、systemd 服务、时钟同步修复和 CloudWatch agent 打进镜像。镜像共享给 demo 账号，Packer manifest 把镜像 ID 传给下一个任务。
3. **在 demo 账号中**，工作流用这个镜像创建新的启动模板版本，并设为默认版本。
4. **实例刷新。** 随后发起实例刷新：替换过程中至少保持一半容量健康，最多可以临时运行到一倍半的容量，每台新实例有三分钟预热时间。
5. **由健康检查决定。** Auto Scaling 组使用负载均衡器对 `/actuator/health` 的健康检查，新实例有十分钟的宽限期。工作流轮询直到刷新完成；如果新实例始终无法变为健康，刷新就不会成功完成。
6. **实例启动时**，user data 从 Secrets Manager 取出数据库密码，写入权限受限的环境文件，并启动 CloudWatch agent，因此镜像里不包含任何机密。

一次成功运行（从构建镜像到刷新完成）的中位耗时为{{fact:deploy_median}}。因为没有更早的基线，这只是耗时本身，不代表提升。

**比看上去弱的地方。** 健康检查把 `200` 到 `499` 的任何状态码都视为健康，因此一台对所有请求都返回客户端错误的实例也能通过。合并后的构建跳过了测试，绕过 PR 检查的改动就会未经测试地上线。

## 谁能访问什么 {#boundaries}

第二个设计问题是运行时边界：哪个组件可以和哪个组件通信，拥有什么权限。

- **网络。** 每个可用区各有一个公有子网和一个私有子网，只有负载均衡器面向公网。实例没有公网 IP，通过一个 NAT 网关访问外网。SSH 规则和明文 HTTP 监听器在开发过程中都已移除。
- **安全组互相引用。** 安全组之间互相引用，而不是写 IP 网段：负载均衡器接受 Web 流量，实例只接受来自负载均衡器、发往应用端口的流量，数据库只接受来自实例和 Lambda 函数的 MySQL 连接。
- **按组件划分的角色。** 实例角色只能访问一个存储桶、所需的四把密钥、一个机密和一个 SNS 主题；Lambda 角色可以读取它的两个机密和对应密钥。日志和指标权限仍使用通配符，密钥策略还给了实例角色并不需要的管理操作——所以我称这些角色为"按组件限定"，而不是"最小权限"。
- **密钥与机密。** {{fact:kms_keys}} 把客户托管的 KMS 密钥，分别用于 S3、实例磁盘、RDS 和 Secrets Manager，并自动轮换。数据库密码由 Terraform 生成并存入 Secrets Manager。
- **可用性与成本。** 应用层跨三个可用区，但数据库和 NAT 网关都是单可用区。其中任何一个所在可用区故障都会导致服务中断；换来的是课程作业的月度固定成本保持在低位。

## 作业里程碑 {#planning}

提交历史读起来像一串里程碑，每一步都通过 PR 合入：先是带测试的 API，然后是 CI，接着是镜像与基础设施即代码（IaC），再到数据层、可观测性、负载均衡，最后是事件、密钥和无服务器邮件。

## 可观测性 {#observability}

两个基于 AOP 的拦截器分别测量每次控制器调用（按状态码计数并计时）和每次仓储层调用（成功数、错误数和耗时）。Micrometer 通过 StatsD 把指标发给 CloudWatch agent，应用输出结构化 JSON 日志，由 agent 发送到 CloudWatch Logs。CPU 告警驱动逐台扩容和缩容的伸缩策略。系统没有监控看板，也没有告警通知：指标可以画图，但我没有搭建看板。

## 异步邮件验证 {#email}

用户注册时，API 向 SNS 发布一个事件后立即返回。VPC 内的 Lambda 函数（Python）接收事件，通过 Mailgun 发送验证链接；链接中带有一次性、很快过期的令牌。这个函数有自己的 CI 工作流，先把新版本发布到 dev 账号，再发布到 demo 账号。

## 不足与下一步 {#limits}

- **从未压测。** 伸缩策略存在，但从来没有压测实际触发过它们，因此我不对服务的伸缩能力做任何声明。
- **宽松的健康检查**和**合并时跳过测试**（见上文）。两者都只需一行改动：匹配 `200`，并在合并构建中运行测试。
- **平铺的 Terraform。** 一个根模块，状态保存在本地，并且手动 apply。下一步：拆分成可复用的模块，并使用带锁的远程状态。
- **长期有效的 CI 密钥。** 工作流使用以 secret 保存的访问密钥。我会改用 GitHub 的 OIDC 联合身份，后来在 KK Knock 的流水线中我就是这样做的。
- **测试偏少。** 三个 REST Assured 测试类覆盖一个正向流程、一个反向流程和若干边界情况，包括一组并发请求。没有单元测试，也没有覆盖率报告。
- **IAM 范围偏宽。** 收紧日志权限中的通配符和 KMS 密钥策略。
