## 后端与 AWS 基础设施 {#overview}

我实现用户、商品和图片 API，配置 AWS 基础设施，并自动化镜像发布。

- **计算。** Spring Boot 运行在 Packer 构建的机器镜像上，由一个三到五台实例的 Auto Scaling 组承载，实例位于跨 {{fact:azs}} 个可用区的私有子网中，前面是 HTTPS 应用负载均衡器和 Route 53 别名记录。
- **数据。** RDS MySQL，用 Flyway 管理迁移，Hibernate 只做表结构校验；商品图片存放在 S3。
- **邮件。** 我实现注册事件经 SNS 触发 Lambda，由函数通过 Mailgun 发送含一次性验证链接的邮件；另用 GitHub Actions 打包函数并发布到 dev 和 demo。
- **域名与 HTTPS。** 我配置 Route 53 到 ALB 的别名记录、使用导入 TLS 证书的 HTTPS 监听器，以及 Mailgun 所需的 DKIM、MX 和 TXT 邮件域名记录。
- **两个 AWS 账号。** 镜像在 dev 账号构建，再发布到 demo 账号。

除了 SNS 主题和 TLS 证书是手动创建的，其余全部由 Terraform 定义。

## CI/CD 发布流程 {#delivery}

每次发布都是一个新的机器镜像，由 Auto Scaling 组用它替换现有实例。发布时不需要登录服务器，也不在原机器上打补丁。

1. **检查。** 每个 PR 都会触发两个工作流：一个在 JDK 21 上、连接 MySQL 服务容器运行测试；另一个用 `fmt`、`init` 和 `validate` 检查 Packer 模板。这两项检查就是准入门槛，合并后的构建不会再跑一遍测试。
2. **构建。** 合并后，工作流在 dev 账号构建 jar，Packer 把 jar、systemd 服务、时间同步修复和 CloudWatch agent 一起打包进镜像。Packer 的 manifest 把镜像 ID 传给下一个任务。
3. **发布。** 镜像共享给 demo 账号，工作流在那里用它创建新的启动模板版本，并设为默认版本。
4. **上线。** 随后发起实例刷新：替换过程中至少保留一半容量在线，替换期间最多运行一点五倍的容量，每台新实例有三分钟的预热时间。工作流会轮询，直到刷新结束。
5. **启动。** 实例启动时，user data 从 Secrets Manager 取出数据库密码，写入权限受限的环境文件，并启动 CloudWatch agent，因此镜像里不含任何密钥。

**健康检查能保证什么。** Auto Scaling 组依赖负载均衡器对 `/actuator/health` 的健康检查，新实例有十分钟的宽限期。这项检查把 `200` 到 `499` 之间的任何 HTTP 状态码都视为健康。因此，它能发现没有响应或返回服务器错误的实例（Spring 的健康端点在服务不可用时返回 `503`），但如果一台实例对所有请求都返回客户端错误，它仍然会通过检查。把判定范围收窄到 `200` 只需要改一行。

一次成功的运行，从构建镜像到实例刷新完成，中位耗时为 {{fact:deploy_median}}。

**为什么每次发布都做新镜像。** 在原实例上更新会更快。但构建镜像让每次发布都可以复现，也容易回滚（上一个启动模板版本仍然保留），dev 账号里的错误也不会波及 demo 账号。代价是每次合并都要构建一次镜像。

## 网络与权限设计 {#boundaries}

第二个设计问题是运行时的边界：哪个组件可以访问哪个组件，拥有什么权限。

- **网络。** 每个可用区各有一个公有子网和一个私有子网，只有负载均衡器对外公开。实例没有公网 IP，通过一个 NAT 网关访问互联网。SSH 规则和明文 HTTP 监听器在开发过程中已经删除。
- **安全组相互引用。** 安全组之间互相引用，而不是按 IP 段放行：负载均衡器接受 Web 流量，实例只接受来自负载均衡器的应用端口流量，数据库只接受来自实例和 Lambda 函数的 MySQL 连接。
- **按组件划分权限。** 实例角色只能访问一个存储桶、它需要的四个密钥、一个 secret 和一个 SNS 主题；Lambda 角色只能读取它的两个 secret 和对应密钥。日志和指标权限仍然使用通配符，密钥策略也给了实例角色一些用不到的管理权限，所以这些角色只能算按组件收窄，还不是最小权限。
- **密钥与 secret。** {{fact:kms_keys}} 个客户托管的 KMS 密钥，分别用于 S3、实例磁盘、RDS 和 Secrets Manager，并自动轮换。数据库密码由 Terraform 生成，存入 Secrets Manager。
- **可用性与成本的取舍。** 应用层跨三个可用区，但数据库和 NAT 网关都是单可用区。其中任何一个所在的可用区出故障，服务都会中断；换来的是项目预算内的固定月成本。

## 部署验证 {#validation}

- **运行过的。** 平台通过上面的流水线部署并多次发布，三个仓库共记录了 {{fact:ci_runs}} 次 CI 运行。目前是否还有环境在运行，无法确认。
- **自动伸缩。** 已配置伸缩策略，后续通过压测验证负载下的扩缩容行为。
- **只在 PR 阶段测试。** 如果有修改绕过了 PR 检查，就会未经测试直接上线。在合并后的构建里也运行测试即可解决。
- **测试偏少。** 三个 REST Assured 测试类覆盖了正向流程、反向流程和边界情况，其中包括一组并发请求。没有单元测试，也没有覆盖率报告。
- **Terraform 是扁平结构。** 只有一个根模块，状态保存在本地，手动 apply。下一步是拆成可复用模块，并使用带锁的远程状态。
- **CI 使用长期密钥。** 工作流用的是保存在 secrets 里的访问密钥。我会改用 GitHub 的 OIDC 联合身份，后来在 KK Knock 的流水线里就是这样做的。

## AOP 指标采集与日志监控 {#observability}

我使用 Spring AOP 为控制器层和仓储层编写统一的监控切面，将指标采集与业务逻辑分离。控制器切面按 HTTP 状态码统计调用次数和耗时，仓储切面记录数据库操作的成功次数、错误次数与耗时。

指标通过 Micrometer 和 StatsD 汇集到 CloudWatch agent；结构化 JSON 日志发送至 CloudWatch Logs，便于分析接口与数据库访问情况。基础设施中的 CloudWatch CPU 告警联动 Auto Scaling 扩缩容策略。

## 异步邮箱验证 {#email}

我设计并实现了 SNS → Lambda → Mailgun 的异步邮箱验证流程。用户注册后，后端将验证事件发布到 SNS，由 Python Lambda 函数发送包含一次性、短时有效令牌的验证链接，邮件发送不阻塞注册接口。

Lambda 部署在 VPC 内，并通过独立的 GitHub Actions 工作流依次发布到 dev 和 demo 账号，将函数更新纳入自动化交付。

## 云端部署规划 {#planning}

我按阶段推进应用上云：先实现并测试 API，建立持续集成，再自动化构建镜像与基础设施，接入数据服务和 IAM 权限，随后完善监控、负载均衡和异步邮件。各阶段通过 PR 集成。
