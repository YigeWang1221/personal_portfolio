## 我们测量了什么 {#question}

数据并行能让一个小型语言模型在单个 GPU 节点上走多远，从哪里开始不再划算？我们两人团队在美国东北大学 Explorer 集群的一个节点上，训练了一个 {{fact:params}} 参数的 GPT-2，测量了四件事：

1. 多个并行 worker 能让 OpenWebText 语料的分词快多少。
2. 在 1、2、4 块 V100-SXM2 上的 DDP 强扩展。
3. FSDP 分片在显存和吞吐之间的取舍。
4. NCCL 的两种通信方式：NVLink 点对点与共享内存。

模型代码直接使用上游 nanoGPT，没有修改。我们的工作是数据管线、分布式训练器、实验脚本和测量。

## 并行代码 {#pipeline}

- **分词。** OpenWebText 共 {{fact:corpus_docs}} 篇文档，用 tiktoken 的 GPT-2 BPE 在多个 worker 进程中分词，按 90/10 划分训练集和验证集，写成 `uint16` 二进制文件。训练时通过 `np.memmap` 读取，任何一次运行都不需要把语料整个载入内存；每次运行使用其中 {{fact:subset}} 的数据。
- **DDP。** `torchrun` 为每块 GPU 启动一个进程，每个进程从环境变量读取 rank，加入 NCCL 进程组。模型用 `DistributedDataParallel` 包装，每八个微批次中有七个在 `no_sync()` 下累积梯度，验证集损失通过 `all_reduce` 在各 rank 间取平均。
- **FSDP。** 同一个模型改用 `FullyShardedDataParallel`，分别尝试 `FULL_SHARD`、`SHARD_GRAD_OP` 和 `NO_SHARD`，按 Transformer block 包装，并用 fp16 混合精度训练。
- **测量。** 每次运行由 rank 0 写出一份摘要：每秒 token 数、平均迭代时间、GPU 峰值显存和验证集 perplexity。

## 用 Slurm 自动化实验 {#automation}

实验计划是一个矩阵：GPU 数量（1、2、4）× 策略（DDP 和三种 FSDP 分片模式）× 通信方式（NVLink 或共享内存）。矩阵中的每一格都是一个配置文件加一个 Slurm 脚本：脚本申请指定型号的 GPU、设置 NCCL 环境变量，再启动训练器（多卡运行通过 `torchrun` 启动）。因此任何一次运行都能原样复现，新增一格只需复制一个现有脚本。

- **通信方式是一个开关。** 共享内存的脚本关闭 NCCL 点对点通信（`NCCL_P2P_DISABLE=1`），检查用的运行会记录 NCCL 实际建立的拓扑（`NCCL_DEBUG_SUBSYS=GRAPH`），所以每次运行都能查到自己走的是哪条通路。
- **固定 token 预算。** GPU 数量翻倍时，迭代次数减半。每次运行看到的数据量相同，不同 GPU 数量之间的吞吐可以直接比较。这个选择的代价见后面两节。
- **我会改进的地方。** 所有 DDP 脚本都用同一个作业名写日志，后来的运行覆盖了 NVLink 那几次运行的原始日志。在作业名里加上唯一的运行 ID，并在摘要写出后立即提交，就能避免。

## 结果 {#results}

| 测量项 | 结果 | 条件 |
|---|---|---|
| DDP 吞吐扩展，1 → 4 卡 | {{fact:ddp_scaling}} | 相同 token 预算；单次运行 |
| NVLink 与共享内存通信 | 吞吐相差 {{fact:transport_gap}} | 每八个微批次同步一次梯度 |
| FSDP 与 DDP 的峰值显存 | FSDP 降低 {{fact:fsdp_memory}} | 这个规模下显存主要被激活值占用 |
| 分词，仅靠多进程 | 加速 {{fact:tokenize_mp}} | 八个 worker 进程 |
| 分词，重复运行 | 加速 {{fact:tokenize_repeat}} | 多进程分片加上复用已分词的缓存 |

扩展接近线性，是因为通信很少：每八个微批次才做一次 all-reduce。同样的原因也让两种通信方式的差距很小。

## 吞吐不等于达到同等质量的时间 {#time-to-quality}

固定 token 预算让吞吐比较很干净，但也掩盖了一件事：用四块 GPU 时，训练只走了四分之一的优化步数，每一步的有效批量是原来的四倍。在已提交的日志中，验证集 perplexity 从单卡的 {{fact:ppl_1gpu}}，升到双卡的 {{fact:ppl_2gpu}}，再到四卡的 {{fact:ppl_4gpu}}。

所以，四卡并不是以四倍速度达到同样的模型质量。公平地比较达到同等质量所需的时间，应该让每种配置都训练到同一个目标验证损失，或者让学习率随批量大小调整。下次我会这样测量。

## NVLink、共享内存，以及一次节点混淆 {#transport}

早期的一次比较看起来显示 "PCIe 与 NVLink" 差距很大。后来发现，那是节点之间的差异，而不是通信方式的差异：几次运行被分配到了不同型号的节点上。固定硬件后，差距缩小到 {{fact:transport_gap}}。README 里完整记录了这件事。对我来说，这是整个项目最清楚的一课：在解释一个数字之前，先确认这次运行实际用了什么硬件和拓扑。

## 为什么 FSDP 在这里不划算 {#fsdp}

我们把 FSDP 的几种分片模式和 DDP 做了对比。FSDP 让峰值显存降低了 {{fact:fsdp_memory}}，吞吐略有损失。在这个模型规模下，显存主要被激活值占用，而不是参数、梯度或优化器状态，分片只能减少后者。对这么小的模型，FSDP 不值得它带来的复杂度；只有当参数和优化器状态占主导时，它才开始发挥作用。

本项目使用的是原版 FSDP API，按 block 自动包装。我对 FSDP2（`fully_shard`）的实践只在另一份课程作业里。

## 分词：把并行和缓存分开 {#tokenization}

我们在语料的 {{fact:sample}} 样本上对比了两种做法：

- **`datasets.map(num_proc=…)`**：从单进程的约十六分钟，降到双进程的几秒钟，即 {{fact:tokenize_repeat}}；从 2 个进程到 16 个进程，耗时几乎不变。曲线平坦说明原因不在并行：这部分收益主要来自重复运行时复用已经分好词的缓存。
- **`multiprocessing.Pool.imap`**：八个 worker 单靠并行带来 {{fact:tokenize_mp}} 的加速，调整分块大小又额外提升了 {{fact:chunk_tuning}}。

两个数字放在一起报告，并说明各自的原因，因为只有第二个才是真正的并行加速。

## 方法上的局限 {#limits}

- **单次运行。** 每种配置只跑了一次，平均值里也包含了预热迭代。多次运行并给出置信区间，才能让通信方式差距这样的小差异更可信。
- **只测了 rank 0 的显存。** 峰值显存只在 rank 0 上测量。
- **节点型号不同。** 共享内存和 NVLink 的运行在不同型号的节点上完成。
- **原始日志丢失。** NVLink 运行的原始日志被覆盖，所以扩展结果以区间表示：保留下来的原始日志和报告中的数值略有差异。
- **下一步：** 测量达到目标 perplexity 所需的时间、分析通信开销、记录每个 rank 的显存，并把脱敏后的日志和代码一起公开。
