## 研究问题 {#question}

在单个 GPU 节点上，数据并行能把一个小型语言模型的训练推进到什么程度？又在哪里开始不划算？我们两人团队在美国东北大学 Explorer 集群的一个节点上，训练了一个 {{fact:params}} 参数的 GPT-2，测量了四件事：

1. OpenWebText 语料的 CPU 分词并行。
2. 在一块、两块、四块 V100-SXM2 上的 DDP 强扩展。
3. FSDP 分片在显存与吞吐之间的取舍。
4. NCCL 通信方式：NVLink 点对点与共享内存。

模型代码直接使用上游 nanoGPT，未做改动。我们的工作是数据管线、分布式训练器、实验设计和测量。

## 实验管线 {#pipeline}

- **分词。** 用 tiktoken 的 GPT-2 BPE 在多个 worker 进程上对 OpenWebText（{{fact:corpus_docs}} 篇文档）分词，按 90/10 划分训练集和验证集，写成 `uint16` 二进制文件。训练时通过 `np.memmap` 读取，每次运行使用其中 {{fact:subset}} 的数据。
- **DDP。** `torchrun` 为每块 GPU 启动一个进程，各进程从环境变量读取 rank 并加入 NCCL 进程组。模型用 `DistributedDataParallel` 包装，每 8 个微批次中有 7 个在 `no_sync()` 下只累积梯度，验证集 loss 通过 `all_reduce` 在各 rank 之间取平均。
- **FSDP。** 同一模型改用 `FullyShardedDataParallel`，分别测试 `FULL_SHARD`、`SHARD_GRAD_OP` 和 `NO_SHARD`，按 transformer block 包装，并用 fp16 混合精度训练。
- **测量。** 每次运行由 rank 0 写出汇总：每秒 token 数、平均迭代时间、峰值显存和验证集 perplexity。

## 实验设计 {#plan}

立项时确定了三种并行策略：多进程分词、DDP 和 FSDP。计划随后细化成一个实验矩阵：GPU 数量（一、二、四块）× 策略（DDP 与三种 FSDP 分片模式）× 通信方式（NVLink 或共享内存）。矩阵里的每一格都对应一个配置文件加一个 Slurm 脚本，任何一次运行都能原样复现。

最关键的协议选择是**固定 token 预算**：GPU 数量翻倍时，迭代次数减半。这样每次运行处理的数据量相同，不同 GPU 数量之间的吞吐可以干净地比较。它也有代价，后面的"深入"部分会说明。

## 结果 {#results}

| 测量项 | 结果 | 条件 |
|---|---|---|
| 1 → 4 卡 DDP 吞吐扩展 | {{fact:ddp_scaling}} | 相同 token 预算；单次运行 |
| NVLink 与共享内存通信 | 吞吐差距 {{fact:transport_gap}} | 每 8 个微批次同步一次梯度 |
| FSDP 与 DDP 的峰值显存 | FSDP 低 {{fact:fsdp_memory}} | 该规模下激活值占显存大头 |
| 分词，重复运行 | 加速 {{fact:tokenize_repeat}} | 多进程分片 + 缓存复用 |
| 分词，仅多进程 | 加速 {{fact:tokenize_mp}} | 8 个 worker 进程 |

扩展接近线性，是因为通信很少：每 8 个微批次才做一次 all-reduce。同样的原因，也让两种通信方式的差距很小。

这是两人团队项目，功能由我们共同完成，我也参与调试了队友负责的部分。分词、单卡基线和 DDP 实验是我自己跑的；FSDP 基准测试是团队成果。公开的 README 由我撰写，FSDP 代码和日志也由我合并进仓库。

## 吞吐不等于收敛速度 {#time-to-quality}

固定 token 预算让吞吐比较很干净，却也掩盖了一件事：四卡运行只用了四分之一的优化步数，而每一步的有效 batch 是单卡的四倍。在已提交的日志中，验证集 perplexity 从单卡的 {{fact:ppl_1gpu}} 上升到四卡的 {{fact:ppl_4gpu}}。

所以，四卡并不是以四倍速度达到同样的模型质量。要公平地比较收敛速度，应当让每种配置都训练到同一个目标验证 loss，或者随 batch 大小调整学习率。下次我会按这种方式测量。

## NVLink、共享内存，以及一次节点混淆 {#transport}

为了比较通信方式，共享内存组的运行关闭了 NCCL 点对点通信（`NCCL_P2P_DISABLE=1`），检查用的运行则记录 NCCL 实际构建的拓扑（`NCCL_DEBUG_SUBSYS=GRAPH`）。

早期的一次对比似乎显示"PCIe 与 NVLink"差距很大，后来发现那是节点之间的差异，而不是通信方式的差异：几次运行落在了不同类型的节点上。固定硬件之后，差距缩小到 {{fact:transport_gap}}。这段经过写进了 README；对我来说，这是整个项目最清楚的一课：在解释一个数字之前，先确认这次运行实际用了什么硬件和拓扑。

## FSDP 在这里为何收益有限 {#fsdp}

我们把 FSDP 的几种分片模式与 DDP 做了对比。FSDP 省下了 {{fact:fsdp_memory}} 的峰值显存，吞吐略有损失。在这个模型规模下，显存大部分被激活值占用，而分片只能减少参数、梯度和优化器状态这几部分。对这么小的模型，FSDP 带来的复杂度并不划算；只有当参数和优化器状态成为显存大头时，它才开始体现价值。

本项目使用的是原版 FSDP API，并采用按 block 自动包装的策略。我唯一一次使用 FSDP2（`fully_shard`）是在另一项课程作业中，不属于本项目。

## 分词加速：区分并行与缓存 {#tokenization}

我们在 {{fact:sample}} 的语料样本上对比了两种方式：

- **`datasets.map(num_proc=…)`**：单进程约十六分钟，两进程只要几秒，即 {{fact:tokenize_repeat}}；从两个进程到十六个进程几乎没有变化。曲线是平的，说明原因不在并行：这部分提升主要来自重复运行时对已分词缓存的复用。
- **`multiprocessing.Pool.imap`**：8 个 worker 仅靠并行就带来了 {{fact:tokenize_mp}} 的真实加速，调整分块大小又带来了 {{fact:chunk_tuning}} 的提升。

我把这两个数字连同各自的机制一起给出，因为只有第二个数字衡量的是并行加速。

## 方法局限与改进 {#limits}

- **单次运行。** 每种配置只跑了一次，平均值里也包含了预热迭代。重复运行并给出置信区间，才能让通信差距这类小差异更可信。
- **只测 rank 0 显存。** 峰值显存只在 rank 0 上测量。
- **节点类型不一。** 共享内存组和 NVLink 组运行在不同类型的节点上。
- **原始日志丢失。** 所有 DDP 脚本都写到同一个作业名下，NVLink 运行的原始日志因此被覆盖。这也是扩展倍数以区间给出的原因：保留下来的原始日志与报告中的数字略有不同。使用唯一的运行 ID 并提交日志，就能避免这个问题。
- **下一步：** 测量达到目标 perplexity 所需的时间，剖析通信开销，记录每个 rank 的显存，并随代码公开脱敏后的日志。
