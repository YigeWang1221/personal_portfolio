## 产品 {#product}

要做的事和冒出来的想法，很少挑你有空的时候出现。KK Knock 就是为这些时刻设计的：刚停好车、一手推着购物车、正在做饭。点一下桌面上的 KK Capture 小组件，说出想法，再点一下结束。App 会把它整理成带截止时间的待办（你说的时间会记成截止时间），或者一条研究过、附有来源的想法；内容不足以整理时，不会生成任何条目。

产品遵循四条原则：

- **在手机上转写。** 语音转文字由 Whisper 在手机上完成，录音不会上传。
- **只发送文字。** 为了分类和研究，只把转写后的文字发送给后端和大模型服务。
- **笔记保存在手机上。** 待办和想法存在本地，而不是在线的资料库里。服务端只为应答重试保留每次响应的副本（见下文）。
- **修改只在本地。** 修改、整理和搜索笔记都不会调用大模型。

它刻意不做聊天机器人、项目管理套件或文档编辑器。

## 我负责的部分 {#ownership}

全部由我独立完成：产品定义、Android 客户端、后端、管理后台、部署和测试。五个仓库的每一次提交都出自我手。

## 当前架构 {#architecture}

系统分为两半，数据归属的界线很明确。

- **Android 客户端**（Kotlin Multiplatform、Jetpack Compose）拥有全部笔记。只有一个前台服务有权录音；用 NDK 编译的 whisper.cpp 在手机上完成转写。每条捕捉经由 Room 中的任务队列、由 WorkManager 驱动处理，结果写入 Room，并显示在桌面小组件上。
- **后端**（FastAPI、异步 SQLAlchemy、PostgreSQL 16）负责账号、个人资料、提示词、用量计量和公告。它不保存转写文本，也没有笔记表。与捕捉相关的唯一一张表是幂等（idempotency）缓存，保存每条捕捉返回过的响应，以便重试时不必再次调用大模型。
- **大模型层**与供应商解耦。DeepSeek 模型通过 OpenAI 兼容接口担任分类器，把捕捉判为 TODO、THOUGHT 或 IGNORED；Gemini 结合 Google 搜索为想法做研究。每个槽位根据配置的 URL 选择调用协议。
- **React 管理后台**（TypeScript、Vite）用于管理用户、用量、公告和系统设置，使用独立的管理员认证。

## 采集失败时会发生什么 {#reliability}

一条语音速记要经得起 App 被杀、网络不稳和大模型调用失败，既不能丢，也不能重复入库。每条捕捉在手机上都是一个有明确状态的任务，设计原则是：重试绝不重做已经保存下来的工作。

- **先保存，再进入下一步。** 只有转写文本保存好之后才删除录音，因此转写中途崩溃可以用录音重试。转写文本一旦保存，任务就进入队列，麦克风立即可以用于下一条捕捉。
- **一个任务只由一个 worker 处理。** 后台 worker 用 Room 中的租约认领排队任务，两个 worker 不会同时处理同一条捕捉。
- **按阶段重试。** 转写失败时用保存的录音重试；分类或研究失败时用保存的转写文本重试。临时网络错误的自动重试有次数上限，遵守 `429 Retry-After`，遇到 `401` 不会循环重试。
- **一条捕捉从头到尾只用一个 ID。** 客户端捕捉 ID 在开始录音时生成，之后不再改变。本地记录使用由账号和这个 ID 派生出的稳定 ID，因此回放的结果会覆盖原记录，而不是新增一条。
- **回放而不是重跑。** 服务端按账号和捕捉 ID 保存响应；在 {{fact:idempotency_window}} 内，响应丢失后的重试会拿到同一个结果，不会再次调用大模型，也不会再次计费。

**服务端到底保存了什么。** 服务端不保存转写文本。但幂等缓存确实保存了返回过的响应，也就是生成的待办或想法（包括研究后的文章及其来源），以账号和捕捉 ID 为键。条目超过 {{fact:idempotency_window}} 即视为过期，并在同一捕捉 ID 再次被查询时删除。手机上的转写文本和任务元数据则按各自的保留规则清理。

**已知缺口。** 缓存只保存已完成的响应。如果第一次请求仍在处理时，重试就到达了服务端（例如一次耗时较长的研究调用中途断线），整条管线会再跑一遍，可能被重复计费。服务端"处理中"标记可以补上这个缺口，目前尚未实现。

## 一次迭代：让队列变得可见 {#iteration}

上面的异步队列本身就是一次迭代，而实际使用又暴露出了下一次迭代。

1. **改动。** 以前一次捕捉要等后端返回后，才能开始下一次录音。我把它改成异步：交互部分在转写文本保存后就结束，分类在后台从任务队列中执行。宿主测试通过，手机上的验收仍未完成。
2. **实际使用暴露的问题。** 实际使用中，我从来没有在上一个任务仍在处理时开始新的录音。原因有三：小组件在"转写中、点击无效"和"后台处理中、点击可开始新录音"两种状态下使用同一套图案；App 计算了等待中的任务数，却从未显示；网络、服务端或限流错误会让任务永远停在处理中——自动重试没有带上重试标记，而控制器只处理成功的情况。
3. **范围。** 队列的语义保持不变，只改用户能看到的部分和失败的收尾方式。后台有任务时，小组件显示就绪图案并加上计数；App 增加统一的"最近捕捉"页面，分为失败、进行中和最近完成三组，通过常驻图标进入，每行都有重试、播放和删除。
4. **背后的修正。** 管线提交时一律标记为重试，因为重新提交由队列负责，而捕捉 ID 保证了幂等。成功以外的任何结果都变成可见的失败。租约过期的任务会重新排队。退避唤醒使用独立的任务名，WorkManager 不会再把它丢掉。
5. **验收。** 每个失败都应当出现在列表中并可以重试，下一次捕捉应当在转写文本保存后立即可以开始。这项工作已经决定，正在手机端进行中，尚未提交或验收；上文的"处理中重复"缺口被明确记录为不在本次范围内。

## 如何规划 {#planning}

每个仓库都有写给 AI 编码代理的规则，另有一套共享的项目记忆（项目背景、架构、当前状态和决策日志），让我和代理保持一致。决策日志在大约四周内积累了 {{fact:adrs}} 条记录，每条都写明背景、决策与影响，被取代的决策也会明确标注；上面这次迭代就对应其中两条记录。

工作按阶段拆分，每个阶段都有自己的文档。端侧转写部分有一份需求文档，明确了硬性的阶段边界和增量窗口的设计。2026 年 9 月的一次功能审查梳理了范围，并确定了后续阶段的待办。

## 端侧语音识别 {#asr}

转写按 {{fact:asr_window}} 的增量窗口进行，并以整段转写兜底。这是分窗口的批量处理，不是逐 token 的流式识别。

性能优化是在一台测试手机上、用短合成音频测的，没有控制温度，因此这些数字说明的是趋势，而不是通用基准：

- **运行时选择 ARM64 内核**后，Small 模型的单段转写耗时由 {{fact:asr_before}} 降至 {{fact:asr_after}}。
- **测试后放弃的方案：** Flash Attention 反而让转写变慢；六线程运行不稳定；手机 GPU 上的 Vulkan 出现 `DeviceLost` 错误。App 保持纯 CPU 运行；测试只在一台手机上进行，不代表其他芯片上的表现。
- **即时取消。** 为 whisper.cpp 加入原生中止补丁后，取消尚未开始的转写所需时间由 {{fact:cancel_before}} 变为 {{fact:cancel_after}}；转写过程中发出的取消在 {{fact:cancel_mid_run}} 内返回。

中止补丁在构建时以覆盖层方式应用，打补丁前先校验锚点，因此内置的 whisper.cpp 源码保持固定版本并可校验哈希。语音模型下载时校验 SHA，再以原子替换的方式生效。

## 大模型成本治理 {#cost}

一款免费的消费级 App 调用大模型，必须有硬性上限。每次调用都按供应商、模型和缓存命中情况计量，计数在数据库中原子递增。

- **未知即拒绝。** 遇到价格未知的调用直接拒绝，而不是估算；价格调整只影响之后的用量。
- **预算快照。** 每个套餐都有按计费周期计算的 AI 成本预算，Free、Lite、Pro 的默认值分别为 {{fact:budgets}}。周期开始时预算会复制进该周期，之后的调整不会改变正在进行的周期。计费周期按每个账号自己的起始日期计算。
- **配额与测试例外。** 测试账号不受配额限制，但仍然计量。

## 自托管、测试与运维 {#operations}

**自托管试运行。** 后端运行在自有的 Mac mini 上，使用 Docker Compose：PostgreSQL 的数据放在外部数据卷；FastAPI 服务以非 root 容器运行，并带健康检查；Nginx 提供管理后台、反向代理 API，是唯一对外发布的端口。首次启动的初始化程序只作用于空数据库，备份文件使用受限权限。该部署在 2026 年 9 月通过验收，覆盖 ARM64 构建、健康检查、管理后台路由、未认证访问的边界、重建容器后数据保留，以及备份。

**同一后端的 AWS 路径。** 在选定自托管之前，我先搭建了一条可随时销毁的 AWS 路径：用 Terraform 创建小型 VPC 和一台 EC2，通过 SSM Session Manager 而不是 SSH 管理；CI 流水线负责测试后端、打包可复现的制品、校验摘要，并通过 GitHub OIDC 联合身份构建 Packer AMI，全程不使用静态 AWS 密钥。两者都在 2026 年 8 月成功运行，其中包括一次完整的创建、测试、销毁流程；这条路径现作为备用方案保留。

**强制更新。** 后端决定最低支持的 App 版本，旧版本会收到 HTTP 426 并提示更新。

**测试。** {{fact:tests}} 个自动化测试用例覆盖后端（含 PostgreSQL 集成测试）、Android 客户端（单元测试、宿主测试和设备测试）以及管理后台。诊断日志只记录请求 ID 和耗时，从不记录内容。
