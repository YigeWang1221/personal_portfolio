## 产品 {#product}

要做的事和想法，往往在腾不出手的时候冒出来：刚停好车、推着购物车、正在做饭。用 KK Knock，只要点一下桌面上的 KK Capture 小组件，把想到的说出来，再点一下。App 会把它整理成待办，并带上你提到的截止时间；或者当作一个想法，查资料后写成一篇附有来源的笔记。如果没有值得保留的内容，就什么也不生成。

产品和背后的架构都遵循四条规则：

- **在手机上转写。** Whisper 在设备上运行，音频不会离开手机。
- **只把文字发出去。** 后端和大模型服务商只能看到转写文字。
- **笔记留在手机上。** 待办和想法保存在本地，不放进在线笔记本。
- **编辑不经过大模型。** 修改、整理和搜索笔记都不会调用大模型。

它有意不做聊天机器人、项目管理工具或文档编辑器。

## 让后台队列看得见 {#iteration}

**原本想要的体验。** 转写文字一保存，就可以开始下一次录音；分类和查资料放在后台队列里执行，第一条还在处理时就能记下第二条。2026 年 9 月，我把采集改成了异步流程。

**真实使用暴露的问题。** 翻看手机上的任务记录，我发现没有一次采集是在前一个任务处理期间开始的：我每次都在等。原因出在界面，而不是队列本身。"正在转写、点击无效"和"正在后台处理、可以再录一条"这两种状态，小组件用的是同一张图；App 算出了排队任务的数量，却从不显示；最近采集的列表只有出错后才会出现。

**一个看不见的故障。** 为这次修改检查代码时，我发现了一个真正的 bug：网络、服务器或限流错误会让任务永远停在"处理中"。原因是自动重试发出时没有带上重试标记，而控制器只处理了成功的情况。

**改了什么，没改什么。** 队列的行为保持不变，只改用户能看到的部分，以及失败最终如何收尾。

- 后台有任务时，小组件仍显示"就绪"图案，并加上一个数字；进度圆环只表示正在本地转写。
- 新增一个"最近采集"页面，列出失败、处理中和刚完成的采集，每条都可以重试、播放或删除。页面入口是一个常驻图标。加这个图标，是因为没有任务时我自己也找不到这个列表。
- 除成功以外的结果都会变成可见的失败。重试一律以重试的身份提交：采集 ID 保证了它是幂等的，所以这样做是安全的。租约过期的任务会重新排队；退避唤醒使用独立的任务名称，WorkManager 不会再把它丢掉。

**现在的进度。** 新增的测试覆盖了网络重试、提交未完成、租约过期，以及失败的任务不会从列表里消失。这次修改已在我的手机上验收，我每天都在用；它还没有进入公开发布的版本。有一个缺口是有意留下的，见下一节。

## 采集失败时 {#reliability}

App 被杀、网络不稳、大模型调用失败，语音速记都不能丢，也不能被重复记录。手机上的每次采集都是一个状态明确的任务，规则是：重试时绝不重做已经保存下来的工作。

- **先保存，再进入下一步。** 只有转写文字保存之后才删除音频，所以转写中途崩溃可以用音频重试。文字保存后任务进入队列，麦克风立即空出来。
- **一个任务只由一个 worker 处理。** 后台 worker 通过 Room 中的租约认领排队任务，两个 worker 不会同时处理同一次采集。
- **按阶段重试。** 转写失败，用保存的音频重试；分类或查资料失败，用保存的文字重试。临时网络错误的自动重试有次数上限，遵守 `429 Retry-After`，遇到 `401` 不会循环重试。
- **一次采集，一个 ID。** 客户端采集 ID 在开始录音时生成，之后不再改变。本地记录的 ID 由账号和这个采集 ID 推导而来，重放的结果会覆盖原记录，而不是再建一条。
- **重放，而不是重跑。** 服务端按账号和采集 ID 保存自己返回过的响应。在 {{fact:idempotency_window}} 内，响应丢失后的重试会拿回同一个结果，不会再次调用大模型，也不会再次计费。

**服务端保存了什么。** 不保存转写文字。响应缓存保存的是返回给手机的内容，即生成的待办或想法（包括查资料写成的文章和来源），以账号和采集 ID 为键。条目超过 {{fact:idempotency_window}} 即视为过期，下次查到这个采集 ID 时删除。

**尚未解决的缺口。** 缓存只保存已经完成的响应。如果第一次请求还在执行时重试就到了服务端（例如一次耗时较长的查资料调用中途断线），整条流程会再跑一遍，可能被计费两次。在服务端加一个"处理中"标记就能解决；我把它安排在首次发布之后。

## 在手机 CPU 上转写 {#asr}

音频留在手机上，代价是语音识别要占用手机 CPU 的时间。转写按 {{fact:asr_window}} 的增量窗口进行，整段转写作为兜底：这是分窗口的批量处理，不是逐 token 的流式识别。

我在一台测试手机上试了几种常见的优化手段。测试使用短合成音频，没有控制机身温度，所以这些数字只说明方向，不是基准测试：

- **运行时选择 ARM64 计算内核**，让 Small 模型每段的转写时间从 {{fact:asr_before}} 降到 {{fact:asr_after}}。最终上线的是这个方案。
- **测试后放弃的方案：** Flash Attention 反而更慢，六线程不稳定，手机 GPU 上的 Vulkan 报 `DeviceLost`。App 只用 CPU；一台手机的结果不代表其他芯片。
- **立即取消。** 原生中止补丁把取消一段尚未开始的转写所需的时间从 {{fact:cancel_before}} 降到 {{fact:cancel_after}}；转写途中发出的取消在 {{fact:cancel_mid_run}} 内返回。

补丁在构建时以覆盖层的方式应用，打补丁前会先校验锚点，因此内置的 whisper.cpp 保持固定版本并经过哈希校验。语音模型下载时做 SHA 校验，并以原子方式替换。

## 架构 {#architecture}

系统分为两半，两者之间有一条严格的数据归属边界。

- **Android 客户端**（Kotlin Multiplatform、Jetpack Compose）拥有所有笔记。只有一个前台服务可以录音。用 NDK 编译的 whisper.cpp 在设备上转写。采集任务在 Room 中的任务队列里流转，由 WorkManager 驱动；结果写入 Room，并显示在桌面小组件上。
- **后端**（FastAPI、异步 SQLAlchemy、PostgreSQL 16）负责账号、个人资料、提示词、用量计量和公告。后端没有笔记表，唯一与采集相关的表就是上面提到的响应缓存。
- **大模型层**不绑定具体服务商。DeepSeek 模型通过兼容 OpenAI 的接口调用，负责判断一条采集是 TODO、THOUGHT 还是 IGNORED；Gemini 借助 Google 搜索为想法查资料。每个模型位根据配置的 URL 选择调用协议。
- **React 管理后台**（TypeScript、Vite）管理用户、用量、公告和系统设置，有独立的管理员认证。

## 大模型成本控制 {#cost}

一个免费的消费级 App 调用大模型，必须有硬性上限。每次调用都按服务商、模型和缓存使用情况计量，计数器在数据库中原子递增。

- **默认拒绝。** 价格未知的调用直接拒绝，不做估算。价格调整只影响之后的用量。
- **预算快照。** 每个套餐在每个计费周期都有 AI 成本预算，Free、Lite、Pro 的默认值分别为 {{fact:budgets}}。预算在周期开始时复制进该周期，之后的修改不会影响进行中的周期。周期以每个账号自己的开始日期为锚点。
- **配额与测试例外。** 测试账号不受配额限制，但照样计量。

## 自托管与 AWS 备用方案 {#operations}

**自托管试运行。** 后端用 Docker Compose 运行在我自己的 Mac mini 上。PostgreSQL 的数据放在外部卷上；FastAPI 服务以非 root 容器运行，并带健康检查；Nginx 提供管理后台、反向代理 API，是唯一对外暴露的端口。首次运行的初始化程序只会处理空数据库，备份文件以受限权限写入。

**同一个后端的 AWS 部署路径。** 决定自托管之前，我先搭了一条可随时销毁的 AWS 路径。Terraform 创建一个小型 VPC 和一台 EC2 实例，通过 SSM Session Manager 管理，不开放 SSH。CI 流水线测试后端、打包可复现的制品、校验摘要，再通过 GitHub 的 OIDC 联合身份构建 Packer AMI，全程不使用静态 AWS 密钥。两者都在 2026 年 8 月跑通过，包括一次完整的创建、测试、销毁；这条路径作为备用方案保留。

**强制更新。** 后端决定最低支持的 App 版本，旧版本会收到 HTTP 426 和更新提示。诊断日志只记录请求 ID 和耗时，不记录内容。

## 工作如何组织 {#planning}

每个仓库都有写给 AI 编码助手的说明，另有一份共享的项目记录（背景、架构、当前状态和决策日志），让我和这些助手依据同一套事实工作。决策日志在约四周内积累到 {{fact:adrs}} 条。每条记录写明背景、决策和影响，被取代的决策会注明；上面那次队列迭代就对应其中两条。
