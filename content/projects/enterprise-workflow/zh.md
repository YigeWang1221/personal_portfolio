## 业务场景 {#scenario}

食物救助涉及多个互不隶属的组织：餐馆或超市捐出食物，检验团队确认食物仍可食用，救助网络收集受助人的需求，志愿者团队派出司机。每个人只需要看到自己的工作，而一份捐赠要能自动交到下一个人手里，不靠任何人手动转交。

FoodShelter 把这件事建模成一个系统：每个人登录到某个网络，进入与自己角色对应的工作区，再把请求放进共享队列，把工作交给下一环。

## 我做了什么，哪些是共同完成的 {#contribution}

我们是三人团队，通过功能分支和 PR 协作。

- **我负责的：** 对象模型及其持久化。model 包中的 {{fact:model_classes}} 类由我创建，包括网络、企业、组织、账号、角色、工作队列等类，以及捐赠路径上的全部请求类型；另外还有工具类、应用主框架和按角色分派的登录。
- **共同完成的：** 各个工作流界面。检验、救助匹配、任务调度和司机这几个界面，初版由队友创建，之后我们都持续修改。其中很大一部分提交是我写的，但我不把它们算作我一个人的成果。
- **不是我做的：** 指标看板和 PDF 报表，由队友完成。

## 一份捐赠的完整流程 {#workflow}

下面是代码真正实现的路径。状态值就是代码中写入的字符串。

| 步骤 | 角色 | 代码实际做了什么 |
|---|---|---|
| 捐赠 | 食品提供方 | 创建食品条目和状态为 `Pending` 的请求，并把同一个请求对象同时加入所在组织的队列、捐赠者自己的队列和网络的检验队列 |
| 检验 | 检验员 | 批准时把食品标记为 `accepted` 和 `stored`，并把请求从检验队列移到仓库队列；拒绝时把请求从检验队列中删除 |
| 求助 | 受助人 | 在救助网络的需求收集组织中创建状态为 `Pending` 的需求请求 |
| 匹配 | 救助站助理 | 把一件仓库中的食品与一条待处理需求配对，生成配送任务（`UnPick`）；需求变为 `Matched`，食品变为 `Assigned` |
| 派单 | 任务调度员 | 只接受仍为 `UnPick` 的任务，指派司机，把任务设为 `Waiting to be picked up`，并把司机标记为 `busy` |
| 配送 | 司机 | 先标记 `Picked up`，再标记 `Delivered`；食品变为 `donated`，任务从司机的进行中队列移到已完成队列 |

各个界面之间从不直接调用：每个界面读取一个队列，修改拿到的请求，再把它放进下一个队列。这是设计中真正起作用的部分——新界面只要读取一个队列，就能接入这条流程。

## 谁负责什么：对象模型 {#domain-model}

- **网络（Network）** 是用户登录的单位，持有各企业、用户账号，以及跨企业共享的两个队列：检验队列和仓库队列。
- **企业（Enterprise）** 把同一类组织归在一起（食品、检验、救助网络、志愿者）。它继承自组织类，因此企业本身也能拥有账号和队列。
- **组织（Organization）** 拥有一个工作队列和一份用户账号目录，并声明自己支持哪些角色。
- **用户账号（UserAccount）** 只有一个角色，另有一个个人队列。
- **角色（Role）** 只负责一件事：`createWorkArea()` 为该角色构建工作界面。登录界面先在所选网络中验证账号，再调用这个方法，因此无需针对角色类型写分支判断。
- **工作请求（WorkRequest）** 带有发送方、接收方和状态。食品、配送和需求请求都继承它；配送请求另外记录任务状态和指派的司机。

有一个做法我会保留，另一个我会改掉。把司机的进行中和已完成队列放在司机角色里，让"司机是否空闲"成了一行判断。但请求自身的 `status` 与配送的 `taskStatus` 是两个自由文本字段，同一个对象可能一个字段写着 `Pending`，另一个写着 `Delivered`。

## 设计的代价 {#tradeoffs}

- **队列共享对象。** 请求在队列之间不会被复制，同一个对象同时存在于多个队列中。这样各界面天然一致，无需同步；但任何界面的修改都会立即在所有地方生效，也没有记录是谁改的。
- **业务规则写在界面里。** "只有未分配的任务才能派单"这条规则写在任务调度员的按钮处理函数中，而不是模型方法里。系统没有服务层，因此这些规则难以测试，也容易被绕过。
- **持久化以整个对象图为单位。** 内嵌的 db4o 数据库在用户退出登录或关闭窗口时保存整个系统对象，启动时再整体读取；数据库为空时生成种子数据。这样不需要迁移表结构，但把数据库文件提交进 git 造成了合并冲突。
- **具体的扩展场景。** 如果要新增一种请求（例如卫生用品），需要新增一个请求子类，以及一个 `createWorkArea()` 返回对应界面的新角色，登录界面无需改动。但每个列出工作的界面都用 `instanceof` 过滤并比较状态字符串，所以每个需要显示新请求的界面都得修改，而且编译器帮不上忙。新增企业类型还要在企业工厂的字符串比较里再加一个分支。

## 局限与改进方向 {#limits}

- **状态规则没有在模型中强制执行。** 司机可以不标记取货就直接标记送达；被拒绝的捐赠只是从检验队列中消失，没有任何地方记录"已拒绝"，捐赠者自己的列表也看不到结果。
- **送达的食品会重新出现。** 没有任何代码把已送达的食品移出仓库队列，而救助站助理的列表只隐藏状态为 `Assigned` 的条目。送达后食品被标记为 `donated`，于是又会以"可分配"的状态出现在列表中。这是我写这一页时发现的，项目中一直没有修复。
- **没有自动化测试**，仓库里也没有截图和 README。
- **下一步：** 在模型中用带合法状态转换的枚举取代状态字符串，把队列之间的移动收进模型方法，并在首次运行时由种子数据生成数据库，而不是把它提交进仓库。
