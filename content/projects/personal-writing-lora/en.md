## The problem {#problem}

Generic LLMs write in a generic voice. This platform learns each user's own style: users upload their writing (TXT, Markdown or Word files), the system trains a personal LoRA "style" on a pinned Qwen2.5-7B-Instruct base model, and users then draft long-form Markdown — articles, social posts, video scripts — in a projects-and-chats workspace that runs on their active style. Styles are versioned, so a user can retrain and keep earlier versions.

That is five systems in one: a web product, a training-job queue, GPU training, multi-adapter serving and the cloud platform under them. Built all at once, none of them could be tested until all of them worked. This page is about how I split it, not about results: no real training run has completed yet.

## What I owned {#ownership}

Everything, alone: the UI and UX designs, the API contract, the data model, the architecture, the training pipeline, the serving layer and the Terraform. ## From sketches to a plan that could be built in pieces {#planning}

The design came before the code, and each step narrowed what the next one had to decide:

1. **Wireframes and an ER sketch** (June 2026) fixed the information architecture: projects and chats, styles with versions and status colours, a drafts panel. The entities of the sketch map one to one onto the tables that were later implemented.
2. **An API contract** (late June) defined the `/api/v1` envelope with request IDs, named error codes such as `STYLE_VERSION_NOT_READY` and `TRAINING_JOB_ALREADY_FINISHED`, camelCase at the boundary, and version labels generated by the backend.
3. **A confirmed architecture** (early July) set the component boundaries — product backend, training worker, adapter manager, infrastructure — listed the rejected alternatives explicitly and fixed the IAM invariants.
4. **Frozen contracts.** Before any component was implemented, the interfaces of the training worker, the backend and the serving layer were frozen as JSON Schema and OpenAPI, with valid and deliberately invalid examples. Each component could then be built and tested against the contract alone.
5. **Milestone plans** for training (T0–T5) and serving (W0–W5), each with the scope and status of every milestone and a dated decision log, plus a Terraform task breakdown with decision gates and a dependency overview from state bootstrap to image release.

The plans also record where work stopped, which is what the status on this page is taken from. The early sketches below are shown as history — what the current design grew out of, not the design itself.

## Current architecture {#architecture}

- **Product.** A Next.js app (strict TypeScript, App Router) talks to a FastAPI backend organized as router → service → repository. PostgreSQL holds {{fact:tables}} tables under Alembic migrations, with CHECK constraints guarding status fields. Sessions use HttpOnly cookies with opaque tokens; only their SHA-256 hashes are stored.
- **Training hand-off.** Submitting a training job writes an outbox row in the same transaction; a dispatcher moves it to SQS. A GPU worker claims the job, fine-tunes with QLoRA and publishes the adapter to S3.
- **Serving.** An adapter manager sits in front of vLLM's runtime LoRA API: it loads, unloads and caches adapters and proxies chat and streaming requests.

## Two decisions that changed the design {#decisions}

Both changes are visible because an earlier architecture sketch survives in my design notes; the confirmed design rejects it in writing.

### The worker reports back instead of writing to the database {#decision-callback}

- **Before.** The early sketch had training instances read their job data directly from the database.
- **Recorded reason.** All database reads and writes stay in the backend, and only the backend may read the database credentials. With a single database client, the connection count stays under control without a connection proxy in the first version.
- **After.** Training instances never connect to the database. The job arrives through SQS; status and results go back through an authenticated callback to the backend, and the training role can read only its callback-token secret — an invariant the Terraform enforces.
- **Status.** Implemented on both sides and tested against local fakes. The callback payload and authentication format between backend and worker still have to be aligned before the first real run.

### The Auto Scaling group reclaims instances; they never terminate themselves {#decision-lifecycle}

- **Before.** The early sketch had each training instance shut itself down when its job finished.
- **Recorded reason.** Capacity should have one owner. The group decides how many instances run; an instance signals that it is finished only by releasing its scale-in protection. The permission to terminate instances is reserved for the backend, to clean up instances that stop sending heartbeats — and that cleanup is designed but not implemented.
- **After.** The group scales from zero on queue backlog. Each worker protects its own instance from scale-in while it trains and releases the protection when done; the group then scales in. The backend never launches GPU instances either.
- **Status.** Scale-in protection and the backlog policies are written; the worker does not yet complete the termination lifecycle action. Nothing here has run on AWS.

**A known inconsistency.** The release workflow refuses launch templates that point at the `$Default` or `$Latest` version and uses static access keys, while the Terraform points the backend group at `$Default` and provides OIDC roles. Run against the Terraform-built group, the workflow would fail its own safety check. It has to be reconciled before the first release.

## Safe job hand-off under at-least-once delivery {#job-handoff}

SQS delivers a message at least once, and GPU instances can disappear mid-job. The design assumes both:

- **Outbox.** The backend records the job and its outbox row in one transaction, so a crash between saving a job and queueing it cannot lose the job. Duplicates are handled downstream.
- **One job identity per style version**, so re-queued work is recognized as the same job.
- **Claim by conditional write.** The worker claims a job with a conditional write in S3, so two workers that receive the same message cannot both train it.
- **Lease heartbeat.** While training, the worker extends the message's visibility timeout. If it loses the lease, it stops working.
- **Delete last.** The message is deleted only after the backend confirms the result. Callback retries resend identical bytes, so the backend can deduplicate them.
- **Artifact integrity.** Each adapter goes to an immutable folder per user, job and artifact version, with a manifest and a SHA-256 hash for every file. The `READY` marker is written last, adapters are moved into the cache atomically, and the system never silently falls back to the base model.

## Scale-from-zero training {#scale-from-zero}

The training Auto Scaling group is pinned at zero instances until there is work. Two scaling policies watch a backlog metric — visible messages per running instance — and add capacity when jobs wait. Each worker takes one message, protects its own instance from scale-in while it trains, and releases the protection when it is done; the group scales back in once the backlog alarm clears.

Several alternatives were rejected in writing before implementation:

- The backend never launches GPU instances itself; SQS and the Auto Scaling group do.
- Training instances never terminate themselves; they release protection and let the group reclaim them.
- Training instances never connect to the database; status goes through an authenticated callback.
- No runtime role may write launch templates.

Two integration items are still open: the worker does not yet complete the termination lifecycle action, and the callback payload and authentication format between backend and worker still need to be aligned.

## Multi-LoRA serving {#serving}

Many users' styles should share one GPU. The adapter manager makes that safe:

- **At most one download per adapter** at a time; concurrent requests wait for it.
- **An LRU cache that never evicts an adapter in use.** Under pressure it refuses a load with an explicit 429 or 503 rather than evicting something another user is reading from.
- **Integrity checks.** SHA-256 hashes and the `READY` marker are verified before an adapter is loaded.
- **A bounded queue** and request limits, with `/metrics` and health endpoints.
- **One manager process** by design: correctness first, horizontal scale later.

The vLLM side is a code integration against the runtime LoRA API; vLLM itself is not packaged yet, and the single-GPU smoke test with a real adapter (milestone W2) has not been run.

## Terraform guardrails and IAM {#infrastructure}

The AWS platform is written in Terraform — {{fact:tf_resources}} resource blocks with input validation rules and cross-checks — and verified only with mock-provider tests.

- **Network.** Public, private-application and private-database subnets in two Availability Zones, one NAT gateway, an S3 gateway endpoint and a private Route 53 zone. Security groups reference each other.
- **Compute.** Launch templates enforce IMDSv2 and encrypted disks. There is no SSH (SSM instead) and no public IP on any instance. The backend group follows the launch template's default version, so a release only has to change the image.
- **Data.** RDS PostgreSQL, S3 (versioned, public access blocked, TLS only) and SQS with a dead-letter queue, all encrypted with KMS.
- **Operations.** Log groups, alarms, a dashboard, VPC flow logs, a monthly budget and cost-anomaly alerts.

The IAM invariants from the design notes that the Terraform enforces:

- `iam:PassRole` exists only in the deploy role.
- Only the release roles can write launch templates.
- Runtime roles trust EC2 only.
- The training role can read its callback-token secret but never the database credentials.

One more invariant — letting the backend clean up stray GPU instances, scoped by tags — is designed but not implemented.
