## Design scope and integration work {#problem}

The goal is a platform for training and serving a LoRA from personal writing. I designed the API, data model, component contracts and cloud infrastructure, then organized implementation into milestones and reviewed the AI-assisted code. The engineering challenge was making the training queue, GPU worker and serving layer independently testable before integrating them.

## Component boundaries and contracts {#planning}

The design came before the code, and each step narrowed what the next one had to decide:

1. **Wireframes and an ER sketch** (June 2026) fixed the information architecture: projects and chats, styles with versions and status colours, a drafts panel. The entities of the sketch map one to one onto the tables that were implemented later.
2. **An API contract** (late June) defined the `/api/v1` envelope with request IDs, named error codes such as `STYLE_VERSION_NOT_READY` and `TRAINING_JOB_ALREADY_FINISHED`, camelCase at the boundary, and version labels generated by the backend.
3. **A confirmed architecture** (early July) set the component boundaries — product backend, training worker, adapter manager, infrastructure — listed the rejected alternatives explicitly and fixed the IAM rules.
4. **Contracts before components.** Before any component was implemented, the interfaces between the training worker, the backend and the serving layer were written down as JSON Schema and OpenAPI, with valid and deliberately invalid examples. Each component could then be built and tested against the contract alone, on a laptop, without a GPU.
5. **Milestone plans** for training and for serving, each milestone with its scope and status and a dated decision log, plus a Terraform task breakdown from state bootstrap to image release.

The product, dataset builder, training worker and adapter manager were developed and tested with local fakes before GPU integration. The wireframes and ER sketch show the early design.

## Architecture decisions {#decisions}

An earlier architecture sketch survives in my design notes; the confirmed design rejects two of its ideas in writing.

### The worker reports back instead of writing to the database {#decision-callback}

- **The sketch.** Training instances read their job data directly from the database.
- **Why I changed it.** All database reads and writes stay in the backend, and only the backend may read the database credentials. With a single database client, the connection count stays under control without a connection proxy in the first version.
- **What it became.** Training instances never connect to the database. The job arrives through SQS; status and results go back through an authenticated callback to the backend, and the training role can read only its callback-token secret — a rule the Terraform enforces.
- **The cost.** One more interface to design and version: the callback payload and its authentication are part of the contract.

### The Auto Scaling group reclaims instances; they never terminate themselves {#decision-lifecycle}

- **The sketch.** Each training instance shut itself down when its job finished.
- **Why I changed it.** Capacity should have one owner. The group decides how many instances run; an instance signals that it is finished only by releasing its scale-in protection. The permission to terminate instances is reserved for the backend, to clean up instances that stop sending heartbeats.
- **What it became.** The group scales from zero on queue backlog. Each worker protects its own instance from scale-in while it trains and releases the protection when done; the group then scales in. The backend never launches GPU instances either.
- **The cost.** Scaling in is driven by an alarm, so an idle GPU instance can run a little longer than its job. The backend's clean-up of silent instances is designed but not built.

## Current architecture {#architecture}

- **Product.** A Next.js app (strict TypeScript, App Router) talks to a FastAPI backend organized as router → service → repository. PostgreSQL holds {{fact:tables}} tables under Alembic migrations, with CHECK constraints guarding status fields. Sessions use HttpOnly cookies with opaque tokens; only their SHA-256 hashes are stored.
- **Training hand-off.** Submitting a training job writes an outbox row in the same transaction; a dispatcher moves it to SQS. A GPU worker claims the job, fine-tunes with QLoRA and publishes the adapter to S3.
- **Serving.** An adapter manager sits in front of vLLM's runtime LoRA API: it loads, unloads and caches adapters and proxies chat and streaming requests.

## Safe job hand-off under at-least-once delivery {#job-handoff}

SQS delivers a message at least once, and GPU instances can disappear mid-job. The design assumes both:

- **Outbox.** The backend records the job and its outbox row in one transaction, so a crash between saving a job and queueing it cannot lose the job. Duplicates are handled downstream.
- **One job identity per style version**, so re-queued work is recognized as the same job.
- **Claim by conditional write.** The worker claims a job with a conditional write in S3, so two workers that receive the same message cannot both train it.
- **Lease heartbeat.** While training, the worker extends the message's visibility timeout. If it loses the lease, it stops working.
- **Delete last.** The message is deleted only after the backend confirms the result. Callback retries resend identical bytes, so the backend can deduplicate them.
- **Artifact integrity.** Each adapter goes to an immutable folder per user, job and artifact version, with a manifest and a SHA-256 hash for every file. The `READY` marker is written last, adapters are moved into the cache atomically, and the system never silently falls back to the base model.

## Scale-from-zero training {#scale-from-zero}

The training Auto Scaling group is pinned at zero instances until there is work. Two scaling policies watch a backlog metric — visible messages per running instance — and add capacity when jobs wait. Each worker takes one message, protects its own instance from scale-in while it trains, and releases the protection when it is done; the group scales back in once the backlog alarm clears.

Several alternatives were rejected in writing before implementation:

- The backend never launches GPU instances itself; SQS and the Auto Scaling group do.
- Training instances never terminate themselves; they release protection and let the group reclaim them.
- Training instances never connect to the database; status goes through an authenticated callback.
- No runtime role may write launch templates.

## Multi-LoRA serving {#serving}

Many users' styles should share one GPU. The adapter manager makes that safe:

- **At most one download per adapter** at a time; concurrent requests wait for it.
- **An LRU cache that never evicts an adapter in use.** Under pressure it refuses a load with an explicit 429 or 503 rather than evicting something another user is reading from.
- **Integrity checks.** SHA-256 hashes and the `READY` marker are verified before an adapter is loaded.
- **A bounded queue** and request limits, with `/metrics` and health endpoints.
- **One manager process** by design: correctness first, horizontal scale later.

Serving has run with one trained adapter on one GPU. Loading many users' adapters at once, and proving that one user's requests cannot reach another user's style, is the isolation benchmark that is still ahead.

## Terraform validation and IAM {#infrastructure}

The AWS platform is written in Terraform — {{fact:tf_resources}} resource blocks with input validation rules and cross-checks — tested with mock-provider runs before it was applied.

- **Network.** Public, private-application and private-database subnets in two Availability Zones, one NAT gateway, an S3 gateway endpoint and a private Route 53 zone. Security groups reference each other.
- **Compute.** Launch templates enforce IMDSv2 and encrypted disks. There is no SSH (SSM instead) and no public IP on any instance. The backend group follows the launch template's default version, so a release only has to change the image.
- **Data.** RDS PostgreSQL, S3 (versioned, public access blocked, TLS only) and SQS with a dead-letter queue, all encrypted with KMS.
- **Operations.** Log groups, alarms, a dashboard, VPC flow logs, a monthly budget and cost-anomaly alerts.

The IAM rules from the design notes that the Terraform enforces:

- `iam:PassRole` exists only in the deploy role.
- Only the release roles can write launch templates.
- Runtime roles trust EC2 only.
- The training role can read its callback-token secret but never the database credentials.

One more rule — letting the backend clean up stray GPU instances, scoped by tags — is designed but not implemented. In the public repository, the backend release workflow still expects static access keys and an explicit launch-template version, while the Terraform provides OIDC roles and a `$Default` version; the two have to be reconciled before releases run from that workflow.
