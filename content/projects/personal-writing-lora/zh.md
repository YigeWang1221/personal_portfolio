## 它做什么，为什么难做 {#problem}

通用大模型写出来的都是通用的腔调。这个平台要学会每位用户自己的风格：用户上传自己写的文字（TXT、Markdown 或 Word 文件），系统基于固定版本的 Qwen2.5-7B-Instruct 训练一个个人 LoRA"风格"，之后用户就能在"项目 + 对话"的工作区里，用当前风格撰写长篇 Markdown，比如文章、社交媒体帖子和视频脚本。风格有版本，用户可以重新训练，同时保留旧版本。

这其实是五个系统：Web 产品、训练任务队列、GPU 训练、多适配器推理，以及它们底下的云平台。如果一次性全部建好，任何一部分都要等所有部分都能工作才能测试，而每一小时花在调试集成上的 GPU 时间都要付钱。所以第一步是拆分。

## 拆成可以单独构建的部分 {#planning}

设计先于代码，每一步都缩小下一步需要决定的范围：

1. **线框图和 ER 草图**（2026 年 6 月）确定了信息架构：项目与对话、带版本和状态颜色的风格、草稿面板。草图中的实体与后来实现的数据表一一对应。
2. **API 契约**（6 月下旬）定义了 `/api/v1` 的响应结构：带请求 ID、有 `STYLE_VERSION_NOT_READY`、`TRAINING_JOB_ALREADY_FINISHED` 这样的命名错误码、边界上使用 camelCase，版本号由后端生成。
3. **确定的架构**（7 月初）划定了组件边界：产品后端、训练 worker、适配器管理服务和基础设施；明确写下了被否决的方案，并确定了 IAM 规则。
4. **先写契约，再做组件。** 在实现任何组件之前，训练 worker、后端和推理层之间的接口就用 JSON Schema 和 OpenAPI 写定，并附上有效示例和刻意构造的无效示例。这样每个组件都可以只对照契约开发和测试，在笔记本电脑上就能完成，不需要 GPU。
5. **里程碑计划**：训练和推理各有一份，每个里程碑都写明范围和状态，并附带日期的决策日志；另有一份 Terraform 任务拆分，从状态存储初始化一直到镜像发布。

这个顺序在预期的地方起了作用：产品、数据集构建器、训练 worker 和适配器管理服务都先基于替身完成了开发和测试，不需要 GPU。下面的线框图和 ER 草图是历史资料，展示当前设计从哪里演变而来，而不是设计本身。

## 两个推翻初稿的决定 {#decisions}

我的设计笔记里保留着一份更早的架构草图；确定后的设计以书面形式否决了其中两个想法。

### worker 回调后端，而不是直接写数据库 {#decision-callback}

- **初稿。** 训练实例直接从数据库读取任务数据。
- **为什么改。** 所有数据库读写都留在后端，只有后端可以读取数据库凭据。只有一个数据库客户端，第一版就不需要连接代理也能控制连接数。
- **改成了什么。** 训练实例从不连接数据库。任务通过 SQS 送达；状态和结果通过带认证的回调返回后端。训练角色只能读取它自己的回调令牌 secret，这条规则由 Terraform 强制执行。
- **代价。** 多了一个需要设计和管理版本的接口：回调的内容和认证方式都是契约的一部分。

### 由 Auto Scaling 组回收实例，实例从不自行终止 {#decision-lifecycle}

- **初稿。** 每台训练实例在任务完成后自行关机。
- **为什么改。** 容量应该只有一个管理者。由 Auto Scaling 组决定运行多少台实例；实例只通过解除自己的缩容保护来表示任务完成。终止实例的权限保留给后端，用来清理不再发送心跳的实例。
- **改成了什么。** Auto Scaling 组根据队列积压从零扩容。每个 worker 在训练期间为自己的实例开启缩容保护，完成后解除，随后由 Auto Scaling 组缩容。后端也从不直接启动 GPU 实例。
- **代价。** 缩容由告警驱动，所以空闲的 GPU 实例可能会比任务多运行一小段时间。后端清理失联实例的功能已经设计，但还没有实现。

## 当前架构 {#architecture}

- **产品。** Next.js 应用（严格模式 TypeScript、App Router）调用 FastAPI 后端，后端按 router → service → repository 分层。PostgreSQL 中有 {{fact:tables}} 张由 Alembic 迁移管理的表，状态字段由 CHECK 约束保护。会话使用 HttpOnly Cookie 和不透明令牌，数据库里只保存令牌的 SHA-256 哈希。
- **训练任务交接。** 提交训练任务时，同一个事务里写入一条发件箱记录，再由分发器把它送进 SQS。GPU worker 认领任务，用 QLoRA 微调，并把适配器发布到 S3。
- **推理。** 适配器管理服务位于 vLLM 的运行时 LoRA API 之前，负责加载、卸载和缓存适配器，并代理对话和流式请求。

## 至少一次投递下的安全任务交接 {#job-handoff}

SQS 保证消息至少投递一次，GPU 实例也可能在任务中途消失。设计同时假定这两种情况：

- **发件箱。** 后端在同一个事务里记录任务和它的发件箱记录，所以在保存任务和入队之间崩溃，也不会丢失任务。重复投递由下游处理。
- **每个风格版本只有一个任务标识**，重新入队的工作会被识别为同一个任务。
- **用条件写入认领。** worker 通过 S3 条件写入认领任务，所以即使两个 worker 收到同一条消息，也不会都去训练。
- **租约心跳。** 训练期间，worker 不断延长消息的可见性超时；一旦失去租约就停止工作。
- **最后才删除。** 只有后端确认收到结果后才删除消息。回调重试发送完全相同的字节，后端可以据此去重。
- **制品完整性。** 每个适配器写入按用户、任务和制品版本划分的不可变目录，附带 manifest 和每个文件的 SHA-256 哈希。`READY` 标记最后写入，适配器以原子方式移入缓存；系统不会在用户不知情时退回基座模型。

## 从零扩容的训练 {#scale-from-zero}

训练用的 Auto Scaling 组在没有任务时固定为零台实例。两条伸缩策略观察一个积压指标（每台运行中实例对应的可见消息数），有任务排队时就增加容量。每个 worker 只取一条消息，训练期间为自己的实例开启缩容保护，完成后解除；积压告警解除后，Auto Scaling 组随之缩容。

实现之前，以下几种方案已经以书面形式否决：

- 后端从不自己启动 GPU 实例，这件事交给 SQS 和 Auto Scaling 组。
- 训练实例从不自行终止，而是解除保护，由 Auto Scaling 组回收。
- 训练实例从不连接数据库，状态通过带认证的回调返回。
- 任何运行时角色都不能写启动模板。

## 多 LoRA 推理 {#serving}

多位用户的风格要共用一块 GPU。适配器管理服务保证这件事安全：

- **每个适配器同一时间最多下载一次**，并发请求会等待这次下载。
- **LRU 缓存从不驱逐正在使用的适配器。** 资源紧张时，它会明确以 429 或 503 拒绝新的加载，而不是驱逐另一位用户正在使用的适配器。
- **完整性校验。** 加载适配器之前，先校验 SHA-256 哈希和 `READY` 标记。
- **有界队列**和请求限制，并提供 `/metrics` 与健康检查端点。
- **有意只运行一个管理进程**：先保证正确，再考虑水平扩展。

推理已经在一块 GPU 上用一个训练好的适配器跑通。同时加载多位用户的适配器，并证明一位用户的请求不会用到另一位用户的风格，是尚未进行的隔离基准测试。

## Terraform 护栏与 IAM {#infrastructure}

AWS 平台用 Terraform 编写，共 {{fact:tf_resources}} 个资源块，带输入校验规则和交叉检查；实际 apply 之前先用 mock provider 做了测试。

- **网络。** 跨两个可用区的公有子网、私有应用子网和私有数据库子网，一个 NAT 网关、一个 S3 网关端点和一个私有 Route 53 区域。安全组之间相互引用。
- **计算。** 启动模板强制使用 IMDSv2 和加密磁盘。不开放 SSH（改用 SSM），任何实例都没有公网 IP。后端 Auto Scaling 组跟随启动模板的默认版本，所以发布时只需要更换镜像。
- **数据。** RDS PostgreSQL、S3（开启版本控制、禁止公开访问、只允许 TLS）和带死信队列的 SQS，全部用 KMS 加密。
- **运维。** 日志组、告警、仪表盘、VPC 流日志、月度预算和成本异常提醒。

设计笔记中的 IAM 规则里，Terraform 已经强制执行的有：

- `iam:PassRole` 只存在于部署角色中。
- 只有发布角色可以写启动模板。
- 运行时角色只信任 EC2。
- 训练角色可以读取它的回调令牌 secret，但永远读不到数据库凭据。

还有一条规则（允许后端按标签清理失联的 GPU 实例）已经设计，但尚未实现。在公开仓库中，后端的发布工作流仍然使用静态访问密钥，并要求显式的启动模板版本，而 Terraform 提供的是 OIDC 角色和 `$Default` 版本；要通过这个工作流发布，必须先让两者一致。
