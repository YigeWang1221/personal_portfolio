## 要解决的问题 {#problem}

通用大模型写出来的是通用的腔调。这个平台学习每位用户自己的风格：用户上传自己的文字（TXT、Markdown 或 Word 文件），系统基于固定版本的 Qwen2.5-7B-Instruct 基座模型训练个人 LoRA"风格"，用户再在"项目 + 对话"的工作区里，用当前风格撰写长篇 Markdown：文章、社交媒体帖子、视频脚本。风格有版本，用户可以重新训练并保留旧版本。

这其实是五个系统：Web 产品、训练任务队列、GPU 训练、多适配器推理，以及它们底下的云平台。如果一次性全部建成，任何一个都要等到全部能跑才能测试。本页讲的是我如何拆分它，而不是结果：目前还没有完成过一次真实训练。

## 从草图到可以分块构建的计划 {#planning}

设计先于代码，而且每一步都缩小了下一步需要决定的范围：

1. **线框图与 ER 草图**（2026 年 6 月）确定了信息架构：项目与对话、带版本和状态颜色的风格、草稿面板。草图中的实体与后来实现的表一一对应。
2. **API 契约**（6 月下旬）定义了 `/api/v1` 的响应信封：请求 ID、`STYLE_VERSION_NOT_READY`、`TRAINING_JOB_ALREADY_FINISHED` 这类具名错误码、边界上统一使用 camelCase，以及由后端生成的版本标签。
3. **确认版架构**（7 月初）划定了组件边界（产品后端、训练 worker、适配器管理服务、基础设施），明确列出被否决的方案，并确定了 IAM 不变量。
4. **冻结契约。** 在实现任何组件之前，训练 worker、后端和推理层的接口先以 JSON Schema 和 OpenAPI 冻结，并附有效示例和刻意构造的无效示例。之后每个组件只需对照契约就能单独构建和测试。
5. **里程碑计划**：训练（T0—T5）和推理（W0—W5）各有一份，写明每个里程碑的范围和状态，并附带日期的决策日志；Terraform 另有一份任务拆解，包含决策关卡和从状态初始化到镜像发布的依赖总览。

这些计划也记录了工作停在哪里，本页的状态就取自其中。下面的早期草图作为历史展示：它们是当前设计的起点，而不是当前设计本身。

## 当前架构 {#architecture}

- **产品。** Next.js 应用（严格 TypeScript、App Router）调用 FastAPI 后端，后端按 router → service → repository 分层。PostgreSQL 中有 {{fact:tables}} 张表，由 Alembic 管理迁移，状态字段由 CHECK 约束保护。会话使用 HttpOnly Cookie 和不透明令牌，数据库只保存令牌的 SHA-256 哈希。
- **训练交接。** 提交训练任务时，在同一个事务里写入一条发件箱记录，再由分发器投递到 SQS。GPU worker 认领任务，用 QLoRA 微调，并把适配器发布到 S3。
- **推理。** 适配器管理服务位于 vLLM 的运行时 LoRA API 之前，负责加载、卸载和缓存适配器，并代理对话与流式请求。

## 两处改变了设计的决策 {#decisions}

这两处变化之所以看得见，是因为我的设计笔记里保留了一张更早的架构草图，而确认版设计以书面形式否决了它。

### worker 回调后端，而不是直接写数据库 {#decision-callback}

- **之前。** 早期草图中，训练实例直接从数据库读取任务数据。
- **记录下来的理由。** 所有数据库读写都留在后端，只有后端可以读取数据库凭证。数据库只有一个客户端，第一版不需要连接代理也能控制连接数。
- **之后。** 训练实例从不连接数据库。任务通过 SQS 到达；状态和结果通过带认证的回调交还给后端，训练角色只能读取自己的回调令牌机密——这是由 Terraform 强制执行的不变量。
- **现状。** 两端都已实现，并基于本地替身测试。第一次真实运行之前，后端与 worker 之间回调的数据格式和认证方式仍需对齐。

### 由伸缩组回收实例，实例从不自行终止 {#decision-lifecycle}

- **之前。** 早期草图中，每台训练实例在任务结束后自行关机。
- **记录下来的理由。** 容量只应有一个主人：运行多少台实例由伸缩组决定，实例只通过解除缩容保护来表示"我完成了"。终止实例的权限只保留给后端，用于清理停止发送心跳的实例——而这项清理已经设计，但尚未实现。
- **之后。** 伸缩组根据队列积压从零扩容。每个 worker 训练期间为自己的实例开启缩容保护，完成后解除，随后由伸缩组缩容。后端也从不自己启动 GPU 实例。
- **现状。** 缩容保护和积压伸缩策略已经写好；worker 尚未调用终止生命周期动作的完成接口。这部分从未在 AWS 上运行过。

**一处已知的不一致。** 发布工作流会拒绝指向 `$Default` 或 `$Latest` 版本的启动模板，并使用静态访问密钥；而 Terraform 让后端伸缩组指向 `$Default`，并提供了 OIDC 角色。如果针对 Terraform 创建的伸缩组运行，这个工作流会因自己的安全检查而失败。第一次发布之前必须先解决这个问题。

## 至少一次投递下的安全任务交接 {#job-handoff}

SQS 保证的是"至少投递一次"，GPU 实例也可能在任务中途消失。设计同时考虑了这两点：

- **发件箱。** 后端在同一个事务里写入任务和发件箱记录，因此即使在保存任务和投递之间崩溃，任务也不会丢失；重复投递由下游处理。
- **每个风格版本对应唯一的任务身份**，重新排队的任务能被识别为同一个任务。
- **用条件写入认领。** worker 通过在 S3 上的条件写入认领任务，收到同一条消息的两个 worker 不可能都去训练它。
- **租约心跳。** 训练期间，worker 持续延长消息的可见性超时；一旦失去租约就停止工作。
- **最后才删除消息。** 只有后端确认结果之后才删除消息；回调重试会发送完全相同的字节，后端可以据此去重。
- **产物完整性。** 每个适配器写入按用户、任务和产物版本划分的不可变目录，附 manifest，每个文件都有 SHA-256 哈希；`READY` 标记最后写入，适配器以原子方式移入缓存，系统也绝不会悄悄退回到基座模型。

## 缩容至零的训练 {#scale-from-zero}

训练用的 Auto Scaling 组在没有任务时保持零台实例。两条伸缩策略监控一个积压指标（可见消息数 ÷ 运行中实例数），有任务等待时就扩容。每个 worker 只取一条消息，训练期间为自己的实例开启缩容保护，完成后解除保护；积压告警恢复后，伸缩组再缩容。

有几种方案在实现前就被书面否决了：

- 后端从不自己启动 GPU 实例，这件事交给 SQS 和 Auto Scaling 组。
- 训练实例从不自行终止，而是解除保护，由伸缩组回收。
- 训练实例从不连接数据库，状态通过带认证的回调传回。
- 任何运行时角色都不能修改启动模板。

还有两项集成工作未完成：worker 尚未调用终止生命周期动作的完成接口；后端与 worker 之间回调的数据格式和认证方式仍需对齐。

## 多 LoRA 推理 {#serving}

多个用户的风格应当共享一块 GPU，适配器管理服务保证这件事是安全的：

- **每个适配器同一时间最多下载一次**，并发请求会等待这次下载。
- **不淘汰使用中适配器的 LRU 缓存。** 压力大时，它会明确返回 429 或 503 拒绝加载，而不是把其他用户正在使用的适配器淘汰掉。
- **完整性校验。** 加载前会校验 SHA-256 哈希和 `READY` 标记。
- **有界队列**与请求上限，并提供 `/metrics` 和健康检查接口。
- **有意设计成单个管理进程**：先保证正确，再考虑水平扩展。

vLLM 一侧是针对运行时 LoRA API 的代码集成；vLLM 本身尚未打包，用真实适配器进行的单卡冒烟测试（里程碑 W2）也还没有运行。

## Terraform 护栏与 IAM {#infrastructure}

AWS 平台用 Terraform 编写，共 {{fact:tf_resources}} 个资源块，并带有输入校验规则和交叉检查，目前只经过 mock provider 测试验证。

- **网络。** 两个可用区中划分公有、私有应用、私有数据库三类子网，一个 NAT 网关、一个 S3 网关端点和一个私有 Route 53 托管区；安全组之间互相引用。
- **计算。** 启动模板强制使用 IMDSv2 和加密磁盘；不开放 SSH（改用 SSM），所有实例都没有公网 IP。后端伸缩组跟随启动模板的默认版本，因此发布时只需要替换镜像。
- **数据。** RDS PostgreSQL、S3（开启版本控制、禁止公开访问、只允许 TLS）以及带死信队列的 SQS，全部使用 KMS 加密。
- **运维。** 日志组、告警、监控看板、VPC 流日志、月度预算和成本异常告警。

设计笔记中已经由 Terraform 落实的 IAM 不变量：

- `iam:PassRole` 只存在于部署角色中。
- 只有发布角色可以修改启动模板。
- 运行时角色只信任 EC2。
- 训练角色只能读取自己的回调令牌，永远读不到数据库凭证。

还有一条不变量（允许后端按标签清理失控的 GPU 实例）已经设计，但尚未实现。
