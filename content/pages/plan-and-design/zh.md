本站的项目差别很大：一款移动产品、一次训练基准实验、一套云基础设施、一个贝叶斯模型。但我规划和设计它们的方式是一致的：

- **尽早冻结接口。** LoRA 平台中 worker、后端与推理层之间的契约，在实现代码之前就已经写成 JSON Schema 和 OpenAPI，并附有刻意构造的无效示例。
- **分阶段规划，并让未完成的阶段保持可见。** 下面每一份路线图都标出了哪些已完成、哪些进行中、哪些还没开始。
- **区分已有的和计划中的。** 架构图标注 CURRENT（当前）或 PROPOSED（规划），早期草图标注为历史。
- **说明测了什么、在什么条件下测的**，也说明哪些根本没有测过。

## 选择在 Mac mini 上自托管，而不是用 AWS {#kk-self-hosting}

**背景。** KK Knock 是一款处于 Beta 前阶段的消费级 App，后端规模不大（FastAPI 和 PostgreSQL）；一条可用的 AWS 路径（Terraform、Packer 镜像和基于 OIDC 的 CI 流水线）已经搭建并测试过。

**备选方案。** 保留 EC2 部署，或者在自有的 Mac mini 上用 Docker Compose 运行同一套后端。

**决策。** 选择 Mac mini + Docker Compose；AWS 路径作为测试过、可随时销毁的备用方案保留。

**取舍。** 只有一台主机、位于家庭网络、没有冗余；换来的是 Beta 前阶段没有托管费用，并且完全自主可控。

**证据与现状。** Compose 部署（唯一的对外端口、外部数据卷、首次启动初始化程序、备份）在 2026 年 9 月通过了有日期记录的验收，目前作为自托管试运行；经由隧道的公网 HTTPS 尚未验收。

## 用客户端键实现近似恰好一次的采集 {#kk-idempotency}

**背景。** 一条语音捕捉必须经得起 App 被杀、网络不稳和反复重试，既不能丢失，也不能被重复计费。

**备选方案。** 不做防护、由客户端生成键，或者在服务端设置"处理中"标记。

**决策。** 开始录音时生成客户端捕捉 ID，之后不再改变；手机上保留三层持久化记录；服务端缓存每次返回的响应，有效期 {{fact:kk-knock.idempotency_window}}，重试时直接回放而不是重跑。

**取舍。** 如果重复请求在第一次请求仍在处理时到达，仍可能被重复计费；换来的是服务端从不保存转写文本，缓存里只有已经返回过的响应。

**证据与现状。** 已在采集服务、手机端采集仓储和一次幂等迁移中实现；服务端标记计划中。

## 测试 GPU 与 NPU 之后，选择纯 CPU 语音识别 {#kk-cpu-asr}

**背景。** whisper.cpp 需要在芯片差异很大的 Android 手机上运行。

**备选方案。** 通过 Vulkan 使用 GPU、使用 NPU、Flash Attention，或者在 CPU 上运行时选择 ARM64 内核。

**决策。** 使用 CPU，并在运行时选择内核。

**取舍。** 放弃 GPU 可能带来的加速，减少对 Vulkan 或 NPU 支持的依赖；实际性能仍随设备而异。

**证据与现状。** 在一台测试手机上用短音频测试：运行时选择内核后，Small 模型的转写耗时由 {{fact:kk-knock.asr_before}} 降至 {{fact:kk-knock.asr_after}}；Flash Attention 更慢，Vulkan 出现 `DeviceLost` 错误。该方案已在 App 中使用。

## 缩容至零的 GPU 训练 {#lora-scale-from-zero}

**背景。** 在 LoRA 平台中，训练任务很少，而闲置的 GPU 很贵。

**备选方案。** 由后端自己启动 GPU 实例、让一块 GPU 常驻运行，或者由队列驱动一个平时保持零台实例的 Auto Scaling 组。

**决策。** SQS 加上最小和期望容量均为零的 GPU Auto Scaling 组，按单实例积压量伸缩。worker 训练期间为自己的实例开启缩容保护，并且从不自行终止。

**取舍。** 有冷启动延迟；换来的是没有闲置 GPU 的成本，后端也不需要启动实例的权限。

**证据与现状。** Terraform 先通过了 mock provider 测试，worker 的生命周期基于本地替身测试，随后在 AWS 上实际运行：训练组为一次真实训练任务从零扩容。之后环境已销毁。

## 不淘汰使用中适配器的缓存 {#lora-adapter-cache}

**背景。** 多个用户的 LoRA 适配器共享一块 GPU；加载适配器很慢，显存也有限。

**备选方案。** 每次请求都加载适配器、不设上限地缓存，或者使用保护使用中适配器的 LRU 缓存。

**决策。** 使用不淘汰使用中适配器的 LRU 缓存，每个适配器同一时间只下载一次，并用有界队列明确返回 429 或 503。

**取舍。** 压力大时可能拒绝加载，但绝不会用只加载了一半的适配器提供服务。

**证据与现状。** 已在适配器管理服务中实现，并基于替身测试；在 AWS 的一块 GPU 上，通过 vLLM 加载一个训练好的适配器提供了推理。同时加载多位用户的适配器还没有做基准测试。

## 跨 AWS 账号的镜像发布 {#cloud-immutable}

**背景。** 运行在 Auto Scaling 组中的 Spring Boot 服务需要频繁部署，并且能安全回滚。

**备选方案。** 原地更新正在运行的服务器，或者为每次发布构建新的机器镜像。

**决策。** 每次合并都用 Packer 构建 AMI：在 dev 账号构建，共享给 demo 账号，再通过新的启动模板版本和实例刷新滚动上线。

**取舍。** 比原地更新慢（中位耗时{{fact:cloud-native.deploy_median}}），但版本化镜像可用于回滚，dev 与 demo 使用独立账号。

**证据与现状。** GitHub Actions 工作流及其运行记录；用于项目的多次发布。

## 扩展实验采用固定 token 预算 {#hpc-token-budget}

**背景。** 比较在一块、两块和四块 V100 GPU 上的训练吞吐。

**备选方案。** 固定迭代次数，或者固定 token 预算。

**决策。** 固定 token 预算：GPU 数量翻倍时，迭代次数减半。

**取舍。** 便于在相同 token 预算下比较吞吐，但 GPU 越多，优化步数越少，验证集 perplexity 也更差：单卡为 {{fact:distributed-llm.ppl_1gpu}}，四卡为 {{fact:distributed-llm.ppl_4gpu}}。

**证据与现状。** 配置文件和已提交的日志。
